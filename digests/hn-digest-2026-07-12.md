## 1. [Mesh LLM: distributed AI computing on iroh](https://www.iroh.computer/blog/mesh-llm)
*Mesh LLM：基于 iroh 的分布式 AI 计算*
▲ 141 分 · tionis · [32 评论](https://news.ycombinator.com/item?id=48876505)

📝 **概要**：Mesh LLM 将多台机器上的 GPU 与内存池化为一个 OpenAI 兼容 API，可本地运行、路由至对等节点，或把大模型按层拆成管道跨机执行。声称用两台节点运行 235B 参数混合专家模型达到 16 词/秒，项目提供 40+ 预置模型。

🧭 **联系你的知识背景**：iroh 是一个点对点网络库，提供 NAT 穿越和基于 QUIC 的加密直连，类似 libp2p，让节点通过公钥寻址，无需中心服务器。本文用 iroh 做分布式模型推理的传输层。

**🔑 要点**
- **Mesh LLM** 将多台闲置 GPU 组成一个逻辑推理服务，暴露为 localhost:9337/v1 的 OpenAI 兼容接口。
- 提供**拆分模式**（Skippy），把超大模型按层分区分配到不同节点流水线执行，使单台装不下的模型也能运行。
- 基于 **iroh** 构建，通过公钥寻址的加密 QUIC 连接实现 NAT 穿透、中继回退和直接对等通信，无中心服务器。
- 目前实测 Qwen 235B MoE 在两节点达到 **16 tok/s**，接近可交互速度，但更大规模部署的性能仍待验证。

💬 **讨论**：评论区对分布式推理的实际可用性存在分歧：部分用户质疑网络吞吐会使其慢到不可用，贡献者给出的 16 tok/s 数据则表明接近交互门槛，但节点配置和网络条件未被明确。

🏷️ `分布式推理` · `LLM 部署` · `点对点网络`

## 2. [What xAI's Grok Build CLI Actually Sends to xAI](https://gist.github.com/cereblab/dc9a40bc26120f4540e4e09b75ffb547)

📝 **概要**：通过 mitmproxy 抓包证实：Grok Build CLI 将读取的 .env 密钥等文件内容明文上传，并且无论是否读取，整个仓库（含 git 历史）都会被静默上传至 Google Cloud Storage，12 GB 仓库中 5.1 GB 被传出，是实际模型对话流量的 27,800 倍，且关闭“改进模型”开关无效。

🧭 **联系你的知识背景**：相当于一个 AI 编码助手在未经明确提示的情况下，将你的整个项目目录（包括密钥文件）以及对模型不可见的文件，完整发送到远程云存储。

**🔑 要点**
- **Grok Build CLI 会明文上传被读取文件的内容**，包括 .env 文件中的密钥，直接发送至 xAI 的 API 端点。
- **与读取无关，整个工作区仓库（含 git 历史）都会被上传**，目标为 Google Cloud Storage 桶 `grok-code-session-traces`。

- **关闭“改进模型”设置不影响上传行为**，`/v1/settings` 仍返回 `trace_upload_enabled: true`，上传机制无法在界面中关闭。

## 4. [An agent in 100 lines of Lisp](https://thebeach.dev/posts/lisp-agent/)

▲ 50 分 · jamiebeach · [1 评论](https://news.ycombinator.com/item?id=48823981)

📝 **概要**：作者用 8 行递归循环和一个 eval 工具实现了完整的 AI agent，利用 Lisp 的同像性（代码即数据）让模型自行编写和执行代码来动态扩展能力，技能记录在记忆中并可跨会话恢复，颠覆了固定工具目录的 Agent 设计模式。

🧭 **联系你的知识背景**：Lisp 的同像性指程序本身是列表数据结构，可以像操作普通列表一样生成和运行代码（类似 Python 的 eval 但更深层），这里 agent 把整个 Lisp 语言作为唯一工具，模型通过生成代码字符串来创建新功能。

**🔑 要点**
- Agent 的核心循环仅 **8 行 Lisp 代码**，无需框架或状态机，靠递归传递消息列表。
- 唯一工具是 **eval**，模型可以动态编写并执行 Lisp 表达式，无需预置工具即可完成计算、Web 搜索等任务。
- 记忆直接存储为 **JSON 文件**，无数据库；模型通过读取历史并重新 eval，能将之前编写的技能自动恢复到新会话。
- 与设计时固定工具目录的传统 Agent 不同，这种模式让 **能力在运行时由模型决定**，技能只是被记住的代码。

💬 **讨论**：HN 评论认为这与让 agent 执行 `python -c` 无本质区别，质疑 Lisp 方案的独特性，但一致认同“模型 + 极简控制流”就能产生巨大能力。

## 10. [Ghost Font: A font that humans can read but AI cannot](https://www.mixfont.com/ghost-font)
*幽灵字体：一种人类可读而 AI 不可读的字体*
▲ 201 分 · justswim · [147 评论](https://news.ycombinator.com/item?id=48870381)

📝 **概要**：Ghost Font 通过视频中移动的点阵显示文字，静态截图无信息，人类可读但费力。测试中 GPT 5.5 Pro 分析 19 分钟产生幻觉，但 GPT 5.6 Sol 用光流分析成功解码。评论区有人用 20 行帧差代码轻易破解，表明这种基于运动的隐藏方式并非牢不可破。

🧭 **联系你的知识背景**：类似对抗样本攻击，利用人类视觉系统对运动整合的敏感性，对抗当前多模态模型多基于静态帧分析的方式。

**🔑 要点**
- **Ghost Font** 把字母编码为点阵移动，单帧图像只含噪声，人类通过运动线索识别字母，但阅读体验费力。
- **GPT 5.5 Pro** 分析 19 分钟后幻觉出虚假消息，**GPT 5.6 Sol** 则采用光流和位移图成功解读，耗时约 13 分钟。
- 评论者 **freehorse** 用 20 行帧差代码，简单减帧后 OCR 即还原字母，证明纯运动隐藏极易被算法破解。
- 作者设想未来用于 **CAPTCHA**，但评论普遍认为一旦引起关注，AI 可轻易针对训练，最终仍是猫鼠游戏。

💬 **讨论**：评论区核心分歧：AI 到底能不能读？有人快速用简单算法破解，也有人展示顶级模型耗时但成功解码，共识是实用性有限且非真正安全。
