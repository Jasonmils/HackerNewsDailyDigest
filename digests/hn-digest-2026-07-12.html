Mesh LLM: distributed AI computing on iroh

Mesh LLM：基于 iroh 的分布式 AI 计算

▲ 141 分 · tionis · 32 评论

Mesh LLM 将多台机器上的 GPU 与内存池化为一个 OpenAI 兼容 API，可本地运行、路由至对等节点，或把大模型按层拆成管道跨机执行。声称用两台节点运行 235B 参数混合专家模型达到 16 词/秒，项目提供 40+ 预置模型。

🧭 联系你的知识背景 iroh 是一个点对点网络库，提供 NAT 穿越和基于 QUIC 的加密直连，类似 libp2p，让节点通过公钥寻址，无需中心服务器。本文用 iroh 做分布式模型推理的传输层。

  • Mesh LLM 将多台闲置 GPU 组成一个逻辑推理服务，暴露为 localhost:9337/v1 的 OpenAI 兼容接口。
  • 提供拆分模式（Skippy），把超大模型按层分区分配到不同节点流水线执行，使单台装不下的模型也能运行。
  • 基于 iroh 构建，通过公钥寻址的加密 QUIC 连接实现 NAT 穿透、中继回退和直接对等通信，无中心服务器。
  • 目前实测 Qwen 235B MoE 在两节点达到 16 tok/s，接近可交互速度，但更大规模部署的性能仍待验证。

💬 讨论 评论区对分布式推理的实际可用性存在分歧：部分用户质疑网络吞吐会使其慢到不可用，贡献者给出的 16 tok/s 数据则表明接近交互门槛，但节点配置和网络条件未被明确。

What xAI's Grok Build CLI Actually Sends to xAI

xAI 的 Grok Build CLI 实际上向 xAI 发送了什么

▲ 104 分 · jhoho · 52 评论

通过 mitmproxy 抓包证实：Grok Build CLI 将读取的 .env 密钥等文件内容明文上传，并且无论是否读取，整个仓库（含 git 历史）都会被静默上传至 Google Cloud Storage，12 GB 仓库中 5.1 GB 被传出，是实际模型对话流量的 27,800 倍，且关闭“改进模型”开关无效。

🧭 联系你的知识背景 相当于一个 AI 编码助手在未经明确提示的情况下，将你的整个项目目录（包括密钥文件）以及对模型不可见的文件，完整发送到远程云存储。

  • Grok Build CLI 会明文上传被读取文件的内容，包括 .env 文件中的密钥，直接发送至 xAI 的 API 端点。
  • 与读取无关，整个工作区仓库（含 git 历史）都会被上传，目标为 Google Cloud Storage 桶 `grok-code-session-traces`。
  • 在 12 GB 随机文件（未读取）的测试中，/v1/storage 上传了 5.1 GB，而 /v1/responses 仅 192 KB，比率约为 27,800 倍。
  • 关闭“改进模型”设置不影响上传行为，`/v1/settings` 仍返回 `trace_upload_enabled: true`，上传机制无法在界面中关闭。

Why is it a big deal?

Nvidia invested $2b into CoreWeave for 9% equity stake. CoreWeave is spending $35b in CapEx in 2026. Therefore, Nvidia's investment is only 5.7% of CoreWeave's single year CapEx. The other $32b is coming from other sources that isn't Nvidia. This is hardly circular.

Nvidia invests in Neoclouds because it's a hedge against hyperscalers having too much power, ie designing and prioritizing their own chips, and not fully using Nvidia's rack design. Neoclouds give hyperscalers competition. Neoclouds accept Nvidia investments because it allows them to secure Nvidia chips first, which is a competitive advantage since new Nvidia chips have been as much as ~5-20x more efficient than old Nvidia chips.

Nvidia was planning to directly compete against hyperscalers through DGX Cloud. They cancelled public DGX Cloud access when they found that investing in Neoclouds would accomplish the same goals without having to compete against their biggest customers.

If you're Nvidia, it's smart because Neoclouds that you have a large stake in will deploy your full stack from GPUs to networking to storage racks. They will share valuable usage data back to you so you can design a better next generation. Hyperscalers are likely a lot less cooperative, prefer to use their own designs if possible, and will guard their usage data.

An agent in 100 lines of Lisp

用 100 行 Lisp 实现的 AI Agent

▲ 50 分 · jamiebeach · 1 评论

作者用 8 行递归循环和一个 eval 工具实现了完整的 AI agent，利用 Lisp 的同像性（代码即数据）让模型自行编写和执行代码来动态扩展能力，技能记录在记忆中并可跨会话恢复，颠覆了固定工具目录的 Agent 设计模式。

🧭 联系你的知识背景 Lisp 的同像性指程序本身是列表数据结构，可以像操作普通列表一样生成和运行代码（类似 Python 的 eval 但更深层），这里 agent 把整个 Lisp 语言作为唯一工具，模型通过生成代码字符串来创建新功能。

  • Agent 的核心循环仅 8 行 Lisp 代码，无需框架或状态机，靠递归传递消息列表。
  • 唯一工具是 eval，模型可以动态编写并执行 Lisp 表达式，无需预置工具即可完成计算、Web 搜索等任务。
  • 记忆直接存储为 JSON 文件，无数据库；模型通过读取历史并重新 eval，能将之前编写的技能自动恢复到新会话。
  • 与设计时固定工具目录的传统 Agent 不同，这种模式让 能力在运行时由模型决定，技能只是被记住的代码。

💬 讨论 HN 评论认为这与让 agent 执行 `python -c` 无本质区别，质疑 Lisp 方案的独特性，但一致认同“模型 + 极简控制流”就能产生巨大能力。

Fixed three bugs that made Qwen3.5-122B a daily driver on Mac Studio

修复三个Bug使Qwen3.5-122B成为Mac Studio上的日常使用模型

▲ 9 分 · marzukia · 1 评论

作者在Mac Studio M3 Ultra上调试长上下文推理栈，通过修复三个缓存相关Bug，将130k-token对话的预填充时间从数分钟降至亚秒级，使122B开源模型实现实用级交互速度。关键洞察：混合注意力架构下磁盘缓存是唯一有效缓存，且需保证提示字节稳定、中断路径写入助手回复、清理垃圾检查点。

🧭 联系你的知识背景 文章涉及大模型推理的KV缓存机制，可以类比为提前保存中间计算结果的重用系统：前次对话的注意力计算成果若未损坏，下次提问可直接复用，避免重新计算整个对话历史。

  • 三个Bug分别导致：1）系统提示中每条消息的唯一ID使KV缓存无法匹配；2）模型回复中断时未保存已生成内容，造成历史缺失；3）后台钩子产生的垃圾检查点占满磁盘，挤掉有效缓存。
  • 修复后，同一32k-token提示的预填充时间从冷启动的88秒降至0.64秒，32k上下文时缓存命中可提速137倍。
  • Qwen 3.5 122B采用混合注意力（75% DeltaNet状态空间层+25%密集注意力），长文本下解码速度从55 tok/s缓降至28 tok/s，避免了密集注意力常见的断崖式下降。
  • 作者强调应分开测量预填充吞吐量和解码吞吐量，常见的总吞吐量指标会掩盖实际对话中用户感受到的生成速度（仅28-55 tok/s）。

Show HN: Getting GLM 5.2 running on my slow computer

Show HN: 在我的慢电脑上运行 GLM 5.2

▲ 895 分 · vforno · 230 评论

Colibrì 是一个纯 C 引擎，将 744B 参数的 MoE 模型 GLM-5.2 以 int4 量化在 25GB RAM 消费级笔记本上运行，常驻内存仅 9.9GB，其余专家从磁盘按需流式加载。实测约 0.05–0.1 tok/s，通过更高带宽 NVMe 和更多 RAM 可提升至 2–4 tok/s，展示了大模型本地化部署的新路径。

🧭 联系你的知识背景 这类似于训练时数据批量流式加载，但 Colibrì 是把模型权重从 NVMe 磁盘按需读入，利用操作系统页缓存作为二级缓存，避免将整个 370GB 模型装入内存。

  • 纯 C 引擎，仅 ~1300 行代码，无 BLAS、无 Python 运行时、无 GPU，直接运行 744B 参数的 GLM-5.2。
  • int4 量化后常驻内存仅 9.9GB，21,504 个路由专家按层 LRU 缓存从磁盘流式加载，冷启动每次 token 需读取约 11GB。
  • 在 WSL2 VHDX、~1GB/s 随机读 下实测约 0.05–0.1 tok/s；若用 PCIe 5 NVMe 加 64GB RAM 并锁定热专家，可预期 2–4 tok/s。
  • 利用模型自带的 MTP（多 token 预测）头实现推测解码，在 int8 精度下可获得 2.2–2.8 token/forward 吞吐提升，但冷缓存时可能拖慢，已配备自适应开关。
