## 2. [GigaToken: ~1000x faster Language model tokenization](https://github.com/marcelroed/gigatoken/)
*GigaToken：语言模型分词速度提升约 1000 倍*
▲ 399 分 · syrusakbary · [79 评论](https://news.ycombinator.com/item?id=49010167)

📝 **概要**：GigaToken 将分词速度推至 GB/s 级别，在 AMD EPYC 144 核上达 24.53 GB/s，比 HuggingFace tokenizers 快 989 倍，且输出完全兼容。主要优化为 SIMD 替代正则预分词、缓存已见词映射、减少 Python 交互，对离线预训练数据准备可大幅提速。

🧭 **联系你的知识背景**：分词（tokenization）是将原始文本转换为模型可处理的 token ID 的步骤，在 LLM 预训练的数据准备环节是吞吐瓶颈，此工具直接加速该管道而非推理。

**🔑 要点**
- 在 **AMD EPYC 9565 144 核** 上分词速度达到 **24.53 GB/s**，比 HuggingFace 快近千倍。
- 可作为 HuggingFace 或 tiktoken 的**即插即用替换**，输出完全匹配，API 兼容。
- 核心优化：用 **SIMD** 替代正则引擎进行预分词，缓存重复词的 token 映射，大幅减少分支和线程通信。
- 适用于离线预训练数据准备，能将 Common Crawl 全量文本的分词从数天缩短至**约 6.5 小时**。

💬 **讨论**：评论普遍赞赏工程价值，但指出分词在推理总耗时中占比极小，真正受益场景是离线数据准备；也有人关心单核心效率和完美哈希表的引入。

## 8. [The startup's Postgres survival guide](https://hatchet.run/blog/postgres-survival-guide)
*创业公司的Postgres生存指南*
▲ 332 分 · abelanger · [175 评论](https://news.ycombinator.com/item?id=49005787)

📝 **概要**：一份来自Hatchet的Postgres实战生存手册，覆盖从索引、查询计划到批量写入和自动清理的核心调优技巧，帮助防止数据库在增长中崩溃。

🧭 **联系你的知识背景**：Postgres是关系型数据库，将其查询优化类比为模型推理时的计算图优化：数据库的“查询计划器”会为每条SQL选择执行路径，错误的选择会严重拖慢性能，就像模型用了低效算子。

**🔑 要点**
- **索引**是避免全表扫描的关键，但过多的索引会带来写开销，复合索引需对齐ORDER BY列
- **查询计划器**依赖表统计信息选择是否使用索引，过时的统计可能导致计划器做出糟糕决策，可通过EXPLAIN ANALYZE诊断
- 批量写入使用**SendBatch**可将吞吐量提升约10倍，减少每个查询的往返开销
- 高写入负载下，调整**自动清理（autovacuum）**频率可防止死元组（dead tuples）堆积导致数据库性能退化

💬 **讨论**：评论指出指南遗漏了备份与恢复策略这一关键生产实践，并补充了UUID v7、hash索引、GIN索引等进阶技巧，形成对原文的有力扩展。

🏷️ `Postgres优化` · `数据库调优` · `创业基础设施`

🔥 **回复最多的评论**（frollogaston · 13 回复）：

> This advice is good, but every startup I've worked with has run into lower hanging fruit than this even. Less scaling problems and more just organizational. Usually what fixes that is:
>
> 1. Don't use an ORM.
>
> 2. Use serial PKs, not meaningful fields (article mentions this).
>
> 3. Use jsonb if needed, but sparingly.
>
> 4. Make your source of truth append-only, meaning you only insert, never update or delete. You can have secondary denormalized tables that are mutated, but that's only for performance/convenience and shouldn't be your sot.
>
> 5. Use connection pools, but be mindful of how many connections you're using. You probably don't need PgBouncer unless you've messed something up.
>
> 6. In code, avoid explicit transactions unless there's a clear reason you need them. Usually only need those for denormalized parts. Just take a conn from the pool, do something, commit, return conn to pool. If you're going to keep an xact open, never do long-running stuff in the middle like RPCs. Too often I see people leave xacts open without much thought. Edit: Also don't use SERIALIZABLE xacts almost ever.
>
> 7. Something is probably wrong if you're using explicit locking like SELECT FOR UPDATE.
>
> 8. Don't reinvent a type system by having a single table where each row can mean many different things depending on a "type int" enum col. Seems oddly specific, but for some reason someone always tries this.
>
> 9. Related to above, don't reinvent a graph DB, typically with "node"/"edge" tables that FK into themselves or in a cycle. 99% of the time what you're trying to do is easily solvable with regular normalized tables.

## 9. [Any text-to-SQL benchmark should address difficulties of real-world data stores](https://cacm.acm.org/blogcacm/if-you-think-you-can-do-real-world-text-to-sql/)
*任何文本转 SQL 基准测试都应解决实际数据存储的困难*
▲ 42 分 · shenli3514 · [11 评论](https://news.ycombinator.com/item?id=49013995)

📝 **概要**：纯 LLM 直接生成 SQL 的准确率在真实陈旧数据库上为零，即使加入 RAG 与提示工程也仅提升至 10%+。评论普遍认为，问题核心在于数据质量与语义层缺失，而非模型能力本身。

🧭 **联系你的知识背景**：可以把“语义层”类比为精心设计的特征工程：不直接给模型原始杂乱数据，而是先把业务指标、表关系和清洗逻辑组织成结构化描述，再让 LLM 使用。

**🔑 要点**
- **纯 LLM 零样本文本转 SQL 在真实数据库基准上准确率为 0%**，加入 RAG 和代理逻辑后也仅到 10%+
- **数据质量与文档缺失是 90% 的障碍**，锈蚀的 schema 和模糊的业务定义比 SQL 生成本身更难解决
- 评论建议放弃一次性生成，改为**代理循环**：先探查 schema、跑少量探测查询、再迭代确认结果
- 多数收益由**懂 SQL 的分析师**获得，业务用户直接使用 LLM 生成 SQL 存在验证盲区，可能把错误结果当成正式结论

💬 **讨论**：评论高度共识：直接文本到 SQL 是错误框架，应转向可探查和迭代的代理循环；但对业务用户能否自行验证结果存在分歧。

🏷️ `文本转SQL` · `LLM 基准测试` · `数据工程`

> The biggest issue with business users (who don’t know SQL) writing SQL with an LLM is that there is no one to validate that query and now that business user will treat that LLM response as canon to share in meetings, presentations, and with clients. The LLM may have forgotten a filter, used the wrong definition of revenue, or misunderstood the user’s intent by writing a query that answers their question in the most literal way.
>
